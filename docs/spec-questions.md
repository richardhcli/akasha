## T7.1 — `composes_touched_facet` predicate is undefined in §4.9
- **Where:** `src/akasha/tms/invalidate.py` (`_composes_touched_facet`, inline `# SPEC-QUESTION:`).
- **Narrowest reading taken:** §4.9's pseudocode calls `composes_touched_facet(edge, touched)` but never defines it. The predicate's first two clauses (`facet_binding in touched` / `facet_binding == '*'`) already cover every `composes` edge with a specific or wildcard binding, so this third clause can only add coverage for a `composes` edge with `facet_binding IS NULL` (a whole-node composition, no facet binding). Implemented as: such a whole-node `composes` edge is touched by ANY non-empty `touched` set — any interface break on the target is relevant to a plain "this node composes that node" subscription, regardless of which facet broke. Covered by a unit test (fires on non-empty touched, silent on empty).
- **Resolution:** open.

## T10.2 — export transport: no bulk-enumeration HTTP endpoint exists; CLI is otherwise a pure HTTP client
- **Where:** `src/akasha/cli/main.py` (`export` verb, not yet implemented); §4.11's frozen endpoint table (`docs/mvp-spec.md`); §4.12's CLI verb table (predates M10, does not list `export` — sanctioned separately by the M10 milestone description itself, `docs/mvp-spec.md` line 357).
- **Details:** T10.2's Goal is "render every managed node to canonical markdown under DIR." No `/v1` endpoint enumerates node ids in bulk (`GET /search?q=` requires a real FTS match term — not a "list all" query; `GET /nodes/{id}` is single-node; `GET /sync/status` returns per-root status/violations/pauses, not full canonical text). The sync engine's own write-back path already does the equivalent internally — `sync.reconcile.ProjectionIndex.build(conn)` enumerates every row from `store.list_sync_files(conn)`, and `hub_state_for()` + `contract.render.render()` (T5.8-proven byte-stable) reconstructs each path's current canonical text — but none of that is reachable over HTTP today. Adding a new endpoint to expose it would mutate the frozen §4.11 table and the OpenAPI snapshot (a real spec-surface change, not a Files-list technicality); reading the store directly from the CLI process would make `export` the second verb (after `daemon`) to break the established pure-HTTP-client architecture from T4.8.
- **Narrowest reading taken:** none yet — flagged before implementation rather than silently choosing either a new endpoint (rule 2: never invent endpoints beyond spec) or a silent architecture deviation. Sent to the user; user asked to route to a fable/opus ruling using `vision.md` + `mvp-spec.md` as the basis.
- **Resolution:** **OPTION (b) — new read-only endpoint `GET /v1/sync/export`; the CLI stays a pure HTTP client** (fable, 2026-07-18). Three written invariants force this and nothing written forces the alternative. (1) Spec §1's data-flow invariant is explicit: "every surface (CLI, UI, plugin, future MCP) speaks **only** the localhost API" — option (a) breaks it in the open. (2) Vision §7.11's *governing* invariant (API-first parity): "any capability of any UI must exist as an API endpoint first … **nothing is ever UI-only**." A direct-store export is precisely a CLI-only capability — and export is not plumbing: vision §13 makes "full export always available" the lock-in-resistance moat itself ("both ethics and … the moat"), so the web UI ("download my vault") and the Phase-4 MCP facade (spec §8 hooks: "a facade process importing nothing but the HTTP API") must be able to offer it, which only an endpoint gives them. (3) Vision §7.12 rule 1: "the API spec is the migration boundary … the plugin, web UI, **CLI**, and MCP facade never change during migration" — an `export` verb importing `kernel/store.py` + `sync` internals welds the CLI to the Python daemon's interior, and at the Rust cutover that verb breaks: the exact failure §7.12 exists to prevent. The `daemon` precedent does not extend: vision §7.11's own sentence splits "`akasha daemon` runs the service" from "subcommands speaking to it over the localhost API" — `daemon` is the *server side* of the boundary, `export` is a client capability, and there is no second server. The T8.5b/WAL point makes option (a) *safe*, but safety was never the objection — architecture is, and per the vision §5 F-list discipline a stated reason must be overturned, not side-stepped. Option (c) is rejected on the T8.0 precedent: when a needed endpoint is entailed by the spec's own architecture, the ruling adds it and amends §4.11 in the same stroke — M10 gates the dogfood month, and the design is fully determined by existing machinery (the endpoint serves exactly the reconciler's `H = render(hub_state_for(path))` over `store.list_sync_files`, T5.8-proven byte-stable). Blessed contract: `GET /v1/sync/export` (a route on the existing `routes/sync.py` router — no `app.py` change), read-only, any token class (reads are never proposal-rewritten; per-token rate limits apply); response lists every managed projection ordered by (sync-root name, POSIX-style root-relative path), each item `{sync_root, relative_path, text}` where `text` is the §4.7 canonical render of the hub's *current* state (a backup of truth, independent of the vault's live bytes — a paused or out-of-contract vault file exports the hub's view), plus top-level `unfiled_node_count` (see the scope ruling below). **A GET must mutate nothing:** `hub_state_for`'s enqueue-on-unprojectable-body side effect must be suppressed on the export path (a read-only mode on `sync/reconcile.py` is a sanctioned completion of this ruling). Amendments applied: spec §4.11 gained the `GET /sync/export` row; §4.12 gained the `export` verb, its pure-client definition, and the "`daemon` remains the only non-HTTP verb" clause; the M10 milestone line cross-references them; build-plan T10.2's Files/Steps/DoD corrected to match (T8.1 precedent: a ruling fixes the plan it invalidates). The OpenAPI snapshot must be regenerated in the same implementing change (§6.3 gate).

## T10.2 — export scope: does "every managed node" mean sync-projection-tracked nodes, or every row in the `nodes` table?
- **Where:** `src/akasha/cli/main.py` (`export` verb, not yet implemented).
- **Details:** The build-plan Goal says "every managed node." The codebase already uses "managed" as a defined term (`contract.parser.BlockSet.managed` — a file whose front matter declares `tm: 1`, i.e. under sync-root contract management) distinct from "every node the store has ever minted," some of which may never be linked to any vault file/sync root. Reading "managed" as sync-projection-tracked (every path `store.list_sync_files` knows about) requires zero new enumeration machinery; reading it as "every node row regardless of sync status" requires a brand-new store.py list-all-nodes helper with no existing precedent anywhere in the codebase.
- **Narrowest reading taken:** none yet — flagged alongside the transport question above rather than guessed. Sent to the user; user asked to route to a fable/opus ruling using `vision.md` + `mvp-spec.md` as the basis.
- **Resolution:** **OPTION (a) — "managed node" = sync-projection-tracked; the unit of export is the managed *file*** (fable, 2026-07-18). "Managed" is not an informal word in this system: spec §4.7 defines it ("front-matter key `tm: 1` marks a managed file") and states the projection's unit — "a managed file is a lossless container … the hub owns only anchored lines." Vision §8's in-scope line settles the format question that decides scope: "plain-Markdown export (**the contract doubles as the export format**)." The export format *is* contract grammar v1, and contract grammar v1 is defined only over managed files: a node never projected into one has no defined markdown serialization at all — exporting it would require inventing a filename scheme, front matter, and block ordering (i.e., inventing grammar, forbidden by rule 0.2), and would abandon the lossless-container semantics that make re-export byte-stable. So: export = for every `store.list_sync_files` row with a base snapshot (same skip rule as `ProjectionIndex.build`), write `render(hub_state_for(parse(base)))` to `DIR/<sync_root.name>/<root-relative path>` (§4.4 makes root names UNIQUE, so the layout is deterministic and collision-free). The build-plan DoD's "all nodes" shorthand is controlled by its own Steps' more specific "every managed node." Reading (b) is rejected: a list-all-nodes helper has no precedent because nothing in the MVP renders a bare node to markdown outside a file context, and the lock-in worry it answers is already answered elsewhere — vision §7.12 rule 2 makes the store itself language-neutral ("SQLite plus canonically serialized bytes; never pickle"), so unfiled nodes are never captive. What the vision *does* demand is honesty (invariant 5: "flagged, never guessed"; §7.8: "the UI presents this honestly"): the export must never misrepresent its own completeness. Therefore the endpoint response and the CLI `--json` summary carry **`unfiled_node_count`** — the count of `status='live'` nodes present in no managed projection — disclosed, never silently omitted (the read-only count helper in `store.py` is a sanctioned rule-0.4 completion, T9.2 precedent). If the dogfood month shows that count growing (nodes minted via `akasha new` that never get filed into a vault), a full-store markdown dump is a *new format decision* for a future ruling — not smuggled into T10.2.
