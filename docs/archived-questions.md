## T1.3 — Object/commit content-addressing format and history() ordering unspecified
- **Where:** `src/akasha/kernel/store.py` module docstring (SPEC-QUESTION comment ~line 18) + `create_node`/`commit_node`/`history` docstrings.
- **Narrowest reading taken:** §4.4/§4.5 name `objects.bytes`/`commits.hash` but do not pin down: (a) the node-content blob byte layout — implemented as canonical-JSON `{"body":...,"facets":[...],"task_state":...}` with `kind="node_snapshot"` (facets have no separate DDL table, so they must live in the versioned object blob); `node_type`/`maturity`/`status`/`vetted` stay on the `nodes` row, not versioned; (b) whether `commits.hash` is content-addressed — chose sha256 hex of canonical-JSON of the commit's own fields (git-style), mirroring `objects.hash`, rather than a minted id8; (c) `history(id)` ordering — chose oldest-first (genesis at index 0), by `rowid ASC`. All three are self-contained within `store.py` and independently replaceable, but downstream M1 tasks (T1.4 edges, T1.6 split/merge redirects, T1.8 property suite) now build on them.
- **Resolution:** resolved 2026-07-11 (answered from vision.md + mvp-spec.md at founder's request). **All three readings confirmed.**
  (a) **Confirmed.** §4.3 defines exactly one canonical serialization for hashing ("JSON for hashing objects"), and the §4.4 DDL versions node content only through `objects.bytes` — with no facets table, the versioned interface (facets are "independently versioned" sub-parts, vision §6) must ride in the object blob. `{"body","facets","task_state"}` is precisely the commit-mutable content set; `node_type`/`maturity`/`status`/`vetted` are head-state columns per the verbatim DDL. Keep `kind="node_snapshot"`.
  (b) **Confirmed.** Vision §7.2 adopts "Git's *data model* (content-addressed snapshots + commit DAG)" — git commits are content-addressed — and §4.3's "object hash = sha256 hex of canonical bytes" is the only hashing rule the spec defines. A minted id8 would also misapply §4.1's semantics: id8s (checksummed to catch hand-typing) are for things humans type (nodes, facets); commit hashes are never hand-typed.
  (c) **Confirmed as the frozen convention:** `history(id)` returns oldest-first (genesis at index 0). The spec is silent; oldest-first matches the append-only log's natural reading order and as-of scans. The M4 API layer (`GET /nodes/{id}/history`) must either present this order or explicitly document its own; do not flip the kernel convention.

## T1.7 — S0 GC reachability: literal "S1+ heads/history" vs "any still-referenced object"
- **Where:** `src/akasha/kernel/store.py` `gc_objects()` docstring + inline SPEC-QUESTION comment.
- **Narrowest reading taken:** §4.5 phrases GC reachability as "objects unreachable from any S1+ node or base snapshot," which read literally would permit collecting an object still referenced by a *live S0* node's commits/head — breaking `get_node`/`history` for that node and contradicting §4.5's stronger property-suite invariant "GC never removes a referenced object." Widened reachability to the UNION of (a) every `commits.object_hash` still in the table, (b) every `nodes.head_hash`, (c) every non-NULL `sync_files.base_hash`. Orphans (objects left behind by `delete_node`'s S0 hard-delete, which removes node+commits but keeps objects) are the only rows collected.
- **Resolution:** resolved 2026-07-11 (answered from vision.md + mvp-spec.md at founder's request). **The widening is intended and required.** The two spec sentences reconcile as scope vs. constraint: §4.4's "unreachable from any S1+ node or base snapshot" describes which objects are *eligible in principle* (S0 content carries no permanence guarantee — vision invariant 6, "S0 is for forgetting"), while §4.5's property-suite invariant "GC never removes referenced objects" is the *binding* constraint — and a live S0 node has not been forgotten yet, so its head/history objects are referenced and must survive (`get_node`/`history` must work on every live node). The intended lifecycle is two-step: (1) S0 *node* GC by retention (vision A7: 30-day default, configurable; the scheduled job is T9.3) hard-deletes expired S0 nodes via the `delete_node` path; (2) `gc_objects` then reclaims the now-orphaned objects. The implemented reachable set — all `commits.object_hash` ∪ all `nodes.head_hash` ∪ non-NULL `sync_files.base_hash` — is correct and final.

## T1.6 — split_node `parts` shape, merge_nodes survivor selection, and facets_touched span rule
- **Where:** `src/akasha/kernel/store.py` (`split_node`, `merge_nodes` docstrings + inline SPEC-QUESTION comments); `src/akasha/kernel/commits.py` (`facets_touched`).
- **Narrowest reading taken:** (1) §4.5 lists `split_node(id, parts) -> redirect` but never defines `parts` — implemented as a non-empty list of `create_node`-style kwargs dicts (`node_type`, `body`, optional `facets`/`task_state`/`author`/`message`), one brand-new minted node per entry. (2) §4.5 `merge_nodes(ids) -> redirect` doesn't specify survivor selection — first id in `ids` is kept as survivor, others tombstoned + redirected to it; no content-merge of retired bodies/facets. (3) §4.9 never formally defines `facets_touched` membership — a facet whose ONLY change is its `span` field is NOT counted as touched (span is a source-location detail, not one of added/removed/renamed/version-bumped). T7.2 (full §4.9 heuristic) may revisit (3).
- **Resolution:** resolved 2026-07-11 (answered from vision.md + mvp-spec.md at founder's request). **All three readings confirmed.**
  (1) **Confirmed.** Vision §7.4 defines split as "duplicate-and-trim (content)" performed by the *human/caller* — the kernel primitive correctly takes explicit part payloads (create_node-style dicts) and never invents content. The API layer (T4.4 `POST /nodes/{id}/split`) defines the request shape and passes the human's trimmed parts through.
  (2) **Confirmed, with composition note.** First-id-survivor with no automatic content union is correct *because of* vision invariant 3 (the human is the only writer of truth): a machine-computed content merge would be machine-authored truth. Vision §7.4's "merge(N₁, N₂ → N) … with union review" composes on top of the kernel primitive: the client creates the union node from human-approved content, then calls `merge_nodes([union_id, N₁, N₂])`. Note for T7.6: reassign-inbound-to-first-successor is the mechanical zero-dangling default; T7.6 layers the per-inbound one-click re-adjudication queue (vision §7.4; spec §4.11 "returns redirect + reassignment queue") on top — edges are pre-pointed at a successor so nothing dangles while the human adjudicates each.
  (3) **Confirmed.** A facet's interface-break signal is its `version` field (§4.2: "bumped on interface break of this facet"); vision pillar 3 makes within-facet precision edits "patch-class by construction." A span-only edit that does not bump `version` is precisely such a precision/re-anchoring edit and must not count as touched; if a re-highlight actually changes the facet's meaning, the edit flow must bump `version` — which *is* counted. T7.2 inherits this rule, and should additionally map facet *additions* to `minor` (vision §6 change classes: "Minor — facet added: no invalidation"); the current helper's narrow major/patch split is an acceptable kernel default until then.

## T1.5 — Does S4 (vetted) chain to S3-eligibility, or is it independent?
- **Where:** `src/akasha/kernel/maturity.py` `derive()` docstring + body (`s4 = vetted`).
- **Narrowest reading taken:** §4.6 lists `S2 iff S1-eligible AND ...` and `S3 iff S2-eligible AND ...` (explicitly chained) but `S4 iff vetted flag set by human token` (no chaining clause). Implemented the literal reading: `vetted=True` ⇒ maturity `S4` regardless of whether S1–S3 conditions hold (a vetted node with zero inbound edges still reports S4). Consequence to confirm: whether vetting can/should be applied to a node that isn't already S3, and whether "highest satisfied stage" was meant to imply the ladder must be climbed in order. Also deferred (separate note in the same file): the §4.6 "recomputed inside the same transaction as any mutation that can change the inputs" wiring lives in T1.6 (owner of store.py), not T1.5.
- **Resolution:** resolved 2026-07-11 (answered from vision.md + mvp-spec.md at founder's request). **Independent S4 is correct — literal reading confirmed.** Basis: (a) §4.6 chains S2/S3 explicitly ("S2 iff S1-eligible AND…", "S3 iff S2-eligible AND…") and conspicuously does not chain S4; "highest satisfied stage" evaluates each condition on its own terms. (b) Vision §6: "S1–S3 transitions are automatic consequences of added infrastructure; **only S4 is a user act**" — S4 is deliberately a different *kind* of transition (human decree), not the next rung of the same mechanical ladder. (c) The safety consequence is decisive: if S4 required S3-eligibility, a vetted-but-not-yet-linked node would derive S0 and be hard-deletable and GC-eligible — silently destroying human-vetted content, the one class of content the system must never lose (vision §6: S4 nodes are "exported as verified memory"). `vetted ⇒ S4 ⇒ S1+-class deletion protection` is the desired behavior, not an accident. UI/review flows will in practice vet nodes that are already S3 (and may nudge toward that), but the kernel semantic is unconditional. Follow-up for M4 (T4.4 `POST /nodes/{id}/vet`): the vet mutation changes a maturity input and must call `_recompute_maturity` in the same transaction, exactly like the edge/commit mutations wired in T1.6. The deferred-wiring note is closed — T1.6 landed the recompute wiring.

## T3.5 — E_DUP_ID detection scope: single file/BlockSet, or whole vault?
- **Where:** `src/akasha/contract/linter.py` `_detect_dup_id()` (SPEC-QUESTION comment inline).
- **Narrowest reading taken:** implemented against a single `BlockSet`/file; cross-file duplicate detection deferred to a higher (M5 sync/vault-wide) layer.
- **Resolution:** resolved 2026-07-12 (fable-model founder-authority review — highest-stakes of the M3 batch, since it determines whether M5 needs a new architectural component). **CONFIRMED: `lint()`'s per-file signature is correct and final. The vault-wide half is NOT covered by kernel §4.1's id-minting collision loop, and does NOT require a new registry component beyond what §4.8 already obligates.**
  (1) `lint()` stays per-file: §4.8's pipeline is per-file by construction (`on_change(path)`, `B = base_store.get(path)`), and §4.7's certain-repair rule for E_DUP_ID is defined relative to the per-file base (`sync_files.base_hash` is keyed by `path`) — a repair rule keyed to a per-file base confirms the linter's operating unit is one file. Battery E05 (copy-paste within a file) is the case the certain-repair targets and is already correctly handled.
  (2) The invariant itself ("same anchor twice **in vault**") is vault-wide even though the detection unit is per-file — cross-file copy-without-cut is a real E05-class event that must be caught by a layer that can see across files.
  (3) **Kernel §4.1 does NOT cover this** — reject that premise. §4.1's collision loop guarantees no two *nodes* ever share a minted id8 (ID-namespace uniqueness); E_DUP_ID is a different invariant — no two *vault block occurrences* may claim to project the same node. Pasting an existing anchor into a second file mints nothing, so the kernel mint path never runs and can't prevent it. The linter/reconcile check is the entire mechanism, not a residual sub-case.
  (4) No new registry component needed: §4.8's `H = render(hub_state_for(path))` already obligates M5 (T5.4) to know which nodes project into which file. Per-file `base_hash` blobs are already a materialized vault-wide anchor index, sharded by file — cross-file dup detection is a cheap read against that same mapping during the ordinary per-file cycle (when a `created` op carries a valid id8 whose projection home is a different, still-holding path). No new SQLite table required (§4.4's DDL is verbatim, rule 0.2).
  **Binding caution for T5.4:** battery E04 (cut-paste to another file) must NOT raise E_DUP_ID — a cross-file move arrives as two file events in arbitrary order, and only reconcile-level op correlation (across files, within the reconcile horizon) can distinguish move (E04) from copy-without-cut (cross-file E05). Anything uncertain ⇒ review item, never a guess (§4.8, vision invariant 5).
  **Net ruling / M5 follow-up:** current `lint()` signature is final. `reconcile.py` (T5.4) gains a cross-file dup check reading the node→path projection mapping it must build anyway for `hub_state_for(path)` — a modest T5.4 sub-feature, not a new component.

## T3.6 — Pause-ratio denominator (pre- vs post-cycle blocks) and empty-base behavior
- **Where:** `src/akasha/contract/linter.py` `pause_threshold()` (SPEC-QUESTION comment inline).
- **Narrowest reading taken:** denominator = `len(base.blocks)` (pre-cycle); empty `base.blocks` ⇒ never pauses.
- **Resolution:** resolved 2026-07-12 (fable-model founder-authority review). **CONFIRMED, correct and final.** (a) The denominator must be the pre-storm population because the post-storm one is corrupted evidence: in the worst storm `vault.blocks` degenerates toward empty exactly when the guard matters most (vision R11: bulk-rewrite tools "creating mass contract violations no human made," answered by pause&diff). ## ORCHESTRATION-INCIDENT (not a spec ambiguity, CORRECTED) — Orchestrating turn fabricated premature "worker DONE" reports for T2.1/T2.2, misdiagnosed as worker failure
- **Where:** first parallel cohort dispatch (T2.1 `src/akasha/kernel/ids.py`, T2.2 `src/akasha/kernel/canonical.py`).
- **Original (incorrect) diagnosis:** This entry originally claimed both fleet-workers self-reported `DONE` with fabricated Verify output ("8 passed"/"14 passed") and produced no files. That diagnosis was wrong.
- **What actually happened:** The *orchestrating* turn narrated fake "T2.1/T2.2 complete" results — with malformed pseudo-XML (a leaked `<thinking>` tag, mismatched closing tags) and implausibly fast durations (~3.5s, ~4.2s) — before either background agent's real `<task-notification>` had arrived. The orchestrator then ran real `ls`/`git status` checks, which correctly found no files, but only because the genuine agents were still mid-flight (they took 296s and 411s respectively). This normal async latency was misdiagnosed as "worker hallucination," and T2.1/T2.2 were incorrectly flipped to `BLOCKED`. The real agents finished shortly after with genuine results (14 passed / 18 passed, matching on-disk file mtimes) and both tasks were subsequently flipped to `DONE` correctly — but the false "worker failure" diagnosis was never corrected until follow-up investigation.
- **Root cause (orchestration, not spec, not worker tooling):** `fleet-worker` agents have working `Write`/`Edit`/`Bash` access and executed correctly. The defect is that the orchestrating turn narrated a background agent's outcome instead of waiting for its actual delivered completion signal — a hallucination risk, not a tooling gap.
- **Resolution:** closed — no fleet-worker or dispatch-protocol change needed. Process lesson: never narrate/report a background `Agent` task's result until its real `<task-notification>` (or an explicit `TaskOutput` poll) has actually been received; treat any "result" appearing outside that delivery mechanism as suspect.

## T5.1 — Base snapshot `objects` content shape: raw canonical bytes vs. canonical-JSON-wrapped dict

This keeps `sync_files.base_hash` → `objects.bytes` a direct, unwrap-free path back to the exact canonical file text, and composes with `gc_objects` (T1.7), which treats any non-NULL `sync_files.base_hash` as reachable purely by hash/column lookup, independent of the referenced row's `kind`.
- **Resolution:** RESOLVED 2026-07-13 — narrowest reading accepted as final: a base snapshot's `objects.bytes` is the raw canonical UTF-8 file text (kind `"base_snapshot"`), hashed directly. It gives `sync_files.base_hash → objects.bytes` an unwrap-free path back to the exact canonical text and composes with GC reachability. No change needed.

## T5.1 — `sync_files.contract_version` default on first `base_store.put` of a path
- **Where:** `src/akasha/kernel/store.py` `write_base_snapshot()` docstring/body.
- **Narrowest reading taken:** `sync_files.contract_version` is `NOT NULL` (spec §4.4) but base_store's Steps/DoD never mention it, and `base_store.put`'s signature (build-plan-recommended `put(sync_root_id, path, bytes)`) has no parameter for it. On first `put` of a previously-unknown path, defaults to the literal `1` (the sole value `contract.grammar.CONTRACT_VERSION` currently takes) rather than importing `contract.grammar` from `kernel/store.py`, which would invert the kernel→contract layering (nothing under `kernel/` currently imports from `contract/`). On a re-`put` of an already-managed path, the existing row's `contract_version` is preserved untouched. T5.4 (reconcile pipeline), which actually parses front-matter and knows the file's real observed contract version, may need `base_store`/`write_base_snapshot` to grow an explicit `contract_version` parameter instead of defaulting.
- **Resolution:** RESOLVED 2026-07-13 — T5.4 added the optional `contract_version: int | None = None` parameter to `store.write_base_snapshot(...)`, so the reconcile pipeline now passes the file's real observed front-matter version and the default-to-`1` only applies when no version is supplied. The layering concern is moot (reconcile, in `sync/`, supplies the value; `kernel/store.py` still never imports `contract/`).

## T5.5 — Fork-point provenance for conflict branches
- **Where:** `src/akasha/kernel/store.py` `record_conflict_branch`.
- **Narrowest reading taken:** There is no stored per-node "last-synced commit", so a conflict branch's `parents` is the node's CURRENT head commit at branch-record time, not necessarily the commit the base snapshot `B` reflected when the vault diverged. An honest fork point would require a schema addition (a per-node / per-sync-file last-synced-commit column); the current head is the closest deterministic anchor available without inventing schema or silently guessing which historical commit `B` corresponds to (content-matching would be ambiguous under revert-to-old-content — a banned silent guess).
- **Resolution:** RESOLVED 2026-07-13 (MVP-accepted, defer) — parenting the conflict branch on the current head commit is accepted for the MVP. Honest fork-point provenance would require a per-node/per-sync-file last-synced-commit column (schema addition), deferred post-MVP and revisited only if a concrete use case needs the exact fork point. Content-matching the fork point is a banned silent guess, so head is the correct deterministic choice absent the schema. Not blocking.

## T5.5 — `get_node(as_of=)` resolution across branches (minor/informational)
- **Where:** `src/akasha/kernel/store.py` `get_node` (as_of path).
- **Narrowest reading taken:** `get_node(as_of=...)` resolves `ORDER BY ts DESC, rowid DESC LIMIT 1` over ALL of a node's commits with `ts<=as_of`, with no notion of mainline vs branch. For an as_of instant after a conflict-branch commit but before/without a later mainline commit, it can return the BRANCH object rather than the head object at that instant. §4.5's as-of semantics predate branching (the DAG was single-line before T5.5) and are silent on cross-branch resolution. No code change made.
- **Resolution:** RESOLVED 2026-07-13 (MVP-accepted, defer) — `get_node(as_of=)` stays branch-unaware (ts-ordered over all commits) for the MVP; branch-aware as-of is deferred until a feature needs it. Branch bodies are read via `get_commit_snapshot`, so nothing currently depends on as-of picking mainline-vs-branch. Not blocking.

## T5.5 — Deleted-op conflict has a review but no branch commit (informational)
- **Where:** `src/akasha/sync/reconcile.py` `conflict_branch_handler`.
- **Narrowest reading taken:** When the vault deletes an anchor while the hub concurrently edits the same node (`op.kind=="deleted"`, `op.vault_block is None`), there is no vault-side body to branch — the hub head is already the sole surviving version. The handler enqueues a `cause_kind="conflict"` review (`cause_ref.branch_commit == null`) but records no DAG branch. Deliberate narrowest reading ("no data to preserve vault-side"), called out as an asymmetry with the modified/checkbox/reparented conflict paths (which always branch).
- **Resolution:** RESOLVED 2026-07-13 (accepted) — the asymmetry is correct: a vault-side delete + hub-side edit has no vault body to branch (the hub head is the sole surviving version), so a review with no branch commit is the right, lossless outcome. Final.

## T5.8-1 — E20 5,000-block reconcile perf: O(n²) LCS in `reconcile._compute_ops`
- **Where:** `src/akasha/sync/reconcile.py` `_lcs_ids` (called from `_compute_ops`'s "moved" detection).
- **Narrowest reading taken:** none — this is a confirmed performance BUG, surfaced by battery case E20. Measured ~15s wall time for one `on_change` cycle on a 5,000-block file; spec §6.2 E20 requires <2s. cProfile shows `_lcs_ids`'s O(n²) DP table (~25M `max()` calls) is ~90% of the time, and it runs over the ~5,000 *stable* (unmoved) ids every cycle even when nothing moved. Peak memory (~222MB) is within bounds. T5.8 (tests+fixtures only) could not fix it without editing `reconcile.py` (outside its Files list) and correctly did NOT weaken the <2s assertion.
- **Resolution:** RESOLVED 2026-07-13 — replaced `_lcs_ids` with `_stable_order_ids`: a fast-path returning `set(b_order)` when `b_order == v_order` (the overwhelmingly common case, O(n)) and an O(n log n) patience-sort LIS otherwise, with a greedy-left reconstruction that reproduces the old DP's earliest-match tie-break. The retired DP is kept verbatim as `_lcs_oracle` in `tests/unit/sync/test_reconcile.py` behind a Hypothesis property test proving byte-for-byte equivalence over random permutations. **E20 dropped from ~15s to ~1.2s; `tests/battery` 27/27; `move`/E17 `expected_ops.json` byte-identical (never regenerated).**

## T5.8-2 — Canonical write-back drops any content that isn't a recognized block/embed/ref (losslessness)
- **Where:** `src/akasha/contract/parser.py` `parse()`/`BlockSet`, `src/akasha/contract/render.py` `render()`, `src/akasha/sync/reconcile.py` `hub_state_for()`.
- **Narrowest reading taken (superseded by decision below):** `render()`/`hub_state_for()` only reproduce recognized Blocks/Embeds/Refs, so any vault line that doesn't parse into one (free prose, fenced examples, malformed-checksum or unknown anchors) was silently erased from the managed file the next time write-back triggered — confirmed via direct probe, including on the very FIRST reconcile of an otherwise-unmodified file. This is a general round-trip-losslessness gap for realistic Obsidian notes that mix prose with anchors, well beyond E14/E15. **DESIGN QUESTION for the human:** is a managed (`tm: 1`) file a *pure projection* (only managed blocks allowed; prose legitimately not preserved) or a *lossless container* (non-anchor prose must survive write-back)? PRD §7's "contract sync losslessness" suggests the latter. If lossless, `render()`/`hub_state_for()` need to track and re-emit raw non-block lines by position.
- **Resolution:** RESOLVED (human-decided 2026-07-13, aligned with an architecture review by the `fable` model): a managed (`tm: 1`) file IS a lossless container — lines that are not contract constructs (prose, blanks, fenced examples, unknown/malformed anchors) must survive write-back verbatim by position; the hub owns only anchored lines (now the verbatim sentence added to `docs/mvp-spec.md` §4.7). Implemented additively (task T5.8-2 follow-up fix, no golden file touched): `parser.BlockSet` gained two additive fields, `raw_lines: dict[int, str]` (1-indexed verbatim non-construct lines) and `front_matter: list[str] | None` (verbatim front matter, only when it differs from the canonical 3-line `tm:` form); `parse()` classifies every source line into exactly one of Block / standalone Embed-or-Ref token / `NewRequest` (also raw-captured, so an un-minted `^tm-new` survives) / raw line, with fenced content always raw and never scanned for anchors; `render()` interleaves `raw_lines` back in by `line_no` (new `_KIND_RAW` tie-break, after blocks/embeds/refs; skipped when an embed/ref shares a raw line's `line_no`) and emits `front_matter` verbatim when set. `reconcile.hub_state_for()`'s `except store.NodeNotFoundError` branch now KEEPS the block with its skeleton text (no review — that id was already reviewed as `E_ID_CHECKSUM`/`E_UNKNOWN_ANCHOR` when it first appeared vault-side) instead of dropping it, which is what makes `render(hub_state_for(parse(B))) == B` a genuine fixed point (verified: a first cycle of a prose+anchors file is byte-preserving and the second cycle is quiet). `diff_blocks`/`_compute_ops` needed zero changes (they only ever read `.blocks`/`.new_requests`; raw content is invisible to op computation, by design). Locked by an extended Direction-1 Hypothesis generator in `tests/property/test_contract_roundtrip.py` (interleaves prose/blank/fenced lines, a fake in-fence anchor, and a non-canonical front-matter case), new parser/render/reconcile unit tests, and additive byte-survival assertions on E14/E15 in `tests/battery/test_edit_battery.py`. See the new T5.8-4 entry below for a flagged trade-off this decision surfaces.

## T5.8-4 — Lossless-container decision (T5.8-2) means a hub-side S0 hard-delete no longer removes the vault line
- **Where:** `src/akasha/sync/reconcile.py` `kernel_apply`'s `"deleted"` branch (calls `store.delete_node`, an S0 hard-delete) vs. `hub_state_for`'s new missing-node-keeps-skeleton-text behavior.
- **Narrowest reading taken:** Before T5.8-2, a hub-side S0 hard-delete of a currently-projected node caused that node's anchor to simply vanish from `structure.blocks` on the next `hub_state_for` pass (the old `except NodeNotFoundError: continue` silently dropped it), so the vault line disappeared on write-back — lossy for the deleted content, but at least self-cleaning. Now that a missing-node block is deliberately KEPT (with its last-known skeleton text) so the lossless-container fixed point holds, an S0 hard-delete no longer auto-removes the corresponding vault line either: it survives on disk as an orphaned anchor pointing at a node the kernel no longer has any record of, and is only ever surfaced as `E_UNKNOWN_ANCHOR` if a human later edits that line (triggering a fresh vault-side diff). This is the narrowest reading available without inventing new schema: propagating an S0 hard-delete to the vault file would require a new kernel-side "S0-delete-tombstone" concept (a hard-delete currently leaves zero durable trace to detect from `hub_state_for`, by design — spec §4.5/§4.6 draw a hard line between S0 hard-delete and S1+ tombstone), which is out of scope for this fix.
- **Resolution:** RESOLVED 2026-07-13 (MVP-accepted, defer) — "survive as an orphan anchor, surface as `E_UNKNOWN_ANCHOR` on next touch" is accepted for the MVP (consistent with zero-silent-guesses and preferable to silently vanishing a user-visible line). Propagating a hub-side S0 hard-delete to the vault would need a new S0-delete-tombstone kernel concept; deferred post-MVP.

## T5.8-3 — Cross-file move of an S0 node can silently hard-delete data depending on reconcile order
- **Where:** `src/akasha/sync/reconcile.py` `_compute_ops` "deleted" branch (cross-file ownership check).
- **Narrowest reading taken:** For an S0 node, a plain cut-paste between two files is lossy under the reconcile order matching real-world temporal causality (source loses the anchor before dest gains it): the S0 node is hard-deleted by `kernel_apply` before dest adopts it, and dest then reports `E_UNKNOWN_ANCHOR` for a node that is genuinely gone. - **Resolution:** RESOLVED 2026-07-13 — `_compute_ops`/`diff_blocks` gained an injected `anchor_elsewhere: Callable[[str], str | None] | None = None` (default `None` preserves prior behavior exactly). `Reconciler._make_anchor_elsewhere` supplies a per-cycle scanner scoped to the CURRENT sync root: it `rglob`s the root's `*.md` (skipping the current file), substring-prefilters `contract_anchor(d) in text`, then parse-confirms `d in blocks`; the "deleted" branch WITHHOLDS the op iff a live managed block with that anchor exists in another file (proof of move-in-flight, not a guess), else hard-deletes.
