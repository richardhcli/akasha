# Running the daemon at startup

Full instructions (Task Scheduler + NSSM) live at [`../../autostart-windows.md`](../../autostart-windows.md) — kept at that path since it's the artifact record for build-plan task T4.9. This page exists only so the client doc tree links to it from one place.

**Before relying on Task Scheduler's own restart-on-failure:** a real test on a Windows dev host (force-killing the daemon twice, then polling for 3.5 minutes) found that Task Scheduler's `RestartCount`/`RestartInterval` settings do **not** reliably restart a force-killed long-running process — `LastTaskResult` flips to a failure code and nothing restarts it. `scripts/windows-service/{init,deinit,destroy}.ps1` (documented in [`../../dogfood/windows-service.md`](../../dogfood/windows-service.md)) demonstrate a working fix — a small supervisor-loop wrapper instead of Task Scheduler's own restart logic, confirmed to recover a killed daemon within ~2 seconds, twice in a row — but they're wired to a disposable scratch config/DB/port and take no arguments; they're a reference implementation to adapt (see `New-DaemonWrapperScript` in `scripts/windows-service/lib.ps1`), not something to run as-is against your real vault. For that, either use **Option B (NSSM)** in the full instructions above, or use Task Scheduler's logon trigger (Option A) purely for autostart-at-login and adapt the supervisor-wrapper pattern yourself for crash recovery.

Linux/macOS equivalents (systemd user unit / launchd) are not yet written — `docs/vision.md` §7.9 specifies the intent (autostart per OS) but no task has produced the non-Windows docs yet.
